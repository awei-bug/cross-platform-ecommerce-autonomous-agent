## 坑：HTTP 头非 ASCII 导致 UnicodeEncodeError

- 现象：AI 配置填了 Key 点测试连接报 `'ascii' codec can't encode characters in position 0-3`。position 0-3 对应 4 个中文字符，即 OpenRouter 的 `X-Title: 运营中枢`。
- 根因：httpx 按 latin-1 编码 HTTP 头，非 ASCII 值直接抛 `UnicodeEncodeError`，在请求发出前就失败，跟 Key 是否有效无关。
- 修复：`OPENROUTER_APP_TITLE` 改为 ASCII（`Ops Command Center`），并在 `auth_headers()` 里对每个归因头做 `value.encode("ascii")` 校验，非 ASCII 直接丢弃而不是让它炸。
- 通用约束：本项目任何进入 HTTP 头的常量（Referer、X-Title、User-Agent）必须是 ASCII，中文只能用在中日文响应体里。
- 验证方式：临时起 `http.server` 假服务捕获请求头，跑 `discover_models(get_provider("openrouter"), "http://127.0.0.1:8899/api/v1", "sk-or-test")`，确认 X-Title/Authorization 正确送达且模型解析正常；验证脚本用完即删。

## 坑：`uvicorn --reload` 在本项目环境不生效

- 现象：修完 `X-Title` 后重启带 `--reload`，日志只打印 `WatchFiles detected changes ... Reloading...`，之后没有新的 `Started server process`，请求仍由旧代码处理，报错照旧。
- 判断方法：用新代码在本地进程直连同一接口能成功（拉到 445 个模型），但走 API 仍失败，即可确认服务进程加载的是旧代码。
- 处理：不用 `--reload`，改为 `taskkill /PID <父PID> /T /F` 后手动重启（父 PID 是监听端口的那个）。当前后端以无 reload 方式常驻（task BAnbuC），改后端代码后必须手动重启。
- 验证：重启后 `POST /api/v1/ai/configurations/{id}/test` 返回 200、`连接成功，已发现 445 个模型`、status=connected。
- 补充：OpenRouter 的 `GET /api/v1/models` 不需要有效 Key 也能列出模型，适合做连通性验证。

## 新增「验证模型可用」探活功能

- 需求：模型能列出来不代表能调通，需要一个按钮验证当前模型能否真正使用。
- 后端新增 `POST /api/v1/ai/configurations/{id}/probe`（`routes/ai.py`）：取 `selected_model` 或请求体 `model_id`，发一次最小真实请求（PROBE_PROMPT「只回复两个字：可用」+ `max_tokens=32`），返回 `AiModelProbeResponse{status, model_id, message, preview, latency_ms, is_demo}`。mock 厂商跳过不调用。
- `generate_text()` 新增可选 `max_tokens` 参数，四个适配器分别映射：openai 的 `max_tokens`、anthropic 的 `max_tokens`、gemini 的 `generationConfig.maxOutputTokens`、ollama 的 `options.num_predict`。
- 探活**不受** `ai_live_generation_enabled` 限制（用户显式点击、单次成本极低），但生成任务仍受该开关保护。
- 401/403 单独映射为「API Key 无效，或当前账号没有该模型的访问权限」，避免只显示 HTTP 状态码。
- 前端 `AiSettingsView.vue` 每个配置卡片加「验证模型可用」按钮 + 结果卡（状态/耗时/模型回复预览）；`api/index.ts` 加 `probeModel()`。
- 坑：FastAPI 里 `Annotated[str | None, Body(default=None)]` 会抛 AssertionError，必须写成 `Annotated[str | None, Body(embed=True)] = None`。
- 实测结论：用户保存的 OpenRouter Key 真实调用返回 401（换 `deepseek/deepseek-v4-flash-0731:free` 同样 401），说明 Key 本身无效，而 OpenRouter 的 `/models` 不校验 Key，所以「测试连接成功」是假象。需要用户换一个有效 Key。

## 401 根因定位：存进数据库的根本不是 Key

- 解密后的 `encrypted_api_key` 内容是 `'ascii' codec can't encode characters in position 0-3: ordinal not in range(128)`（80 字符、含空格）——用户把之前那条报错文本当成 Key 粘贴进了输入框。OpenRouter 因此返回 `Missing Authentication header`。
- 诊断方法：临时脚本用 `api_key_for(row)` 解密后只打印长度/前缀/是否含空白（不打印原文），再直连 `/key` 和 `/chat/completions` 打印厂商响应体。用完即删。
- 根因修复：`ai_repository._validate_api_key()` 在加密入库前校验——不能含空格/换行、长度 ≥ 16，否则 422 明确提示，不再等到调用时报 401。
- 路由修正：`PATCH /ai/configurations/{id}` 原先把所有 ValueError 映射成 404，会把校验错误也说成「配置不存在」；现在只有 `AI 配置不存在` 走 404，其余走 422。
- 错误信息增强：`ai_provider_registry.provider_error_detail()` 在 401/403 时附带厂商 `error.message`（清洗空白、截断 120 字符、含 `sk-` 则丢弃，避免回显凭据）。`ai_generation` 与 `discover_models` 共用。新增两个测试覆盖「附加工厂信息」与「不回显凭据」。
- 经验：厂商的「列模型」接口常常不校验 Key，只有真实生成调用才能验证 Key 有效性——这正是探活按钮的价值。

- 三处改进：
  1. `provider_error_detail()` 扩展：401/403/429 都附带厂商 `error.message`，429 另给「已触发限流，请稍后重试或改用其他免费模型」。
  2. 探活对传输层异常（`RemoteProtocolError` / `ConnectError`）自动重试一次；HTTP 错误不重试。
  3. `_reasoning_fallback()`：推理模型常把输出放在 `reasoning_content` / `reasoning` 而 `content` 为空，主内容为空时回退读取这些字段，避免误判「模型返回空内容」。探活 `max_tokens` 也从 32 提到 128，prompt 改为「不要输出思考过程」。
- 认知：OpenRouter 免费模型可用性随上游波动，验证失败优先换模型而不是反复重试同一个。
